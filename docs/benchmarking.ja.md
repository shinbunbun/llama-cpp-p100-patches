# 測り方

English: [benchmarking.md](benchmarking.md)

ここにあるパッチの大半は 0.5〜2% の価値しかない。それを信頼できる形で測るのは書くことより
難しく、実際いくつかは**測定が壊れていたせいで**棄却されかけ、また採用されかけた。以下は
そのために必要だったことである。

## パッチが実際に走る条件で測る

実運用と条件が違ったせいで、独立に 3 回、誤った結論に達した。

**熱**。P100 のブーストクロックは、長い測定の間に 1328 → 1101 MHz (−17%) まで下がる。
逐次に測ると最初に走った構成が有利になり、その差は測ろうとしている効果より大きい。対策は、
候補の前後に必ずベースラインを挟み、各測定の前に GPU が一定温度以下に下がるまで待つことで
ある。これでベースラインの再現性は prefill で ±0.02% になる。

**greedy サンプリング**。投機デコードの受理率を動かす変更は、**現実的なサンプラーで**
測らなければならない。あるパッチは temp 0 / top-k 1 では +7.7% に見えたが、これは greedy が
受理率を 0.99 まで押し上げ、深いドラフトを不当に有利にするためだった。現実的なサンプラーでは
+2.2% だった。

**ハーネス違い**。`llama-bench` には投機デコードが無い。ある変更は llama-bench で +1.4%、
実ワークロードでは **+0.01%** だった。ドラフトモデルが無いと expert の matmul が全部
`ncols_dst = 1` になり、それがまさにその変更の守備範囲だったからである。実ワークロードでは、
そのトラフィックは別のカーネルへ移る。

## 数字を信じる前にノイズ下限を測る

「同一バイナリの A/B でも ±0.4% 振れるので 0.5% 未満は測れない」という見立ては、二重に
誤りだった。**ヌル A/B** (同じバイナリを 2 本の腕に置き、差が原理的にゼロになる測定) を
回すと、次のようになる。

| | SD |
|---|---:|
| 幾何平均 (3 プロンプト) | 0.169% |
| プロンプト A | 0.113% |
| プロンプト B | 0.151% |
| **プロンプト C** | **0.555%** |

誤り 1 は、±0.4% が**最大値**であって平均の分解能ではないことである。4 ラウンドの平均なら
±0.165% になる。誤り 2 は、**分散の約 9 割を 1 本のプロンプトが出していた**ことである
(全体 0.343 のうち 0.555²)。しかも常時振れているのではなく、**16 回中 2 回だけ約 1% 遅い**
二峰性だった。

そのプロンプトを判定から外すだけで SD は 0.169% → 0.068% になり、4 ラウンドで ±0.067% に
なった。これは**実測した 3 プロンプトの値に対して 2.5 倍、当初見込んでいた ±0.4% に対しては
6 倍**の分解能であり、しかもコストはゼロである。クロックは原因ではない (稼働中の 74 サンプル
すべてで 1328 MHz、throttle も全区間 0x0 だった)。

既知の効果で検証もした。ある停止スイッチの A/B は 8 ラウンドで +0.723% ± 0.041% となり、
最初の 4 ラウンドだけでも +0.720% で一致した。副産物として、パッチ 20
(`fuse-add-unary-mul`) の真の値が、当初報告の +0.47% ではなく **+0.72%** だったことも
分かった。

## できる限り「同一バイナリ + 実行時スイッチ」で測る

可能な限り、各パッチには停止スイッチ (`GGML_CUDA_DISABLE_*` / `LLAMA_*=0`) を付けてある。
A/B の両腕が**同じバイナリ**になるので、コード配置・アロケータの状態・ビルドの非決定性が
まとめて比較から消えるからである。

2 バイナリが避けられないときは、同じツリーからパッチだけを外して対照を作り、そのうえで
**成り立つべき向き**を確かめる。**パッチを当て直したものが、元のバイナリとバイト一致
しなければならない。** 一致しないなら、対照はパッチ以外の何かでも違っており、測っている差は
自分が思っているものではない。

**「無改変のはずの腕」を必ず入れること。** あるラウンドの結果は、作業ツリーに棄却済みの
変更が残っていたせいで全部捨てることになった。気づけたのは、no-op のはずの腕が参照ビルドを
3.4% 下回り、レジスタ数も違っていたからである。ベースラインを再現しない対照腕は、入手できる
中で**最も安いバグ検出器**である。これ無しで先へ進んではいけない。

## プロファイルの読み方

**カーネル名ではなく grid X で分解する。** 同じカーネル名の中で、テンソルごとの単価が
27 倍違うことがある。grid X は 行数 / rows_per_block なのでテンソルが一意に決まる。名前で
集計したせいで、発見そのものが平均の下に隠れていた。

**decode のプロファイルから prefill を除外する。** 「カーネル 200 発以上 + busy 50% 超」
だけで生成区間を選ぶと、prompt 処理 (トレースの 30%。dequantize と cuBLAS hgemm が支配的)
や起動時の memset まで拾ってしまい、すべての比率が 3 割ほど薄まる。

**起動回数はペアの証拠になる。** 2 つのカーネルの起動回数が完全に一致するのは、それが
1 対 1 対応である強い証拠である。重複した q8_1 の量子化も、いくつかの融合候補も、この方法で
見つけた。

## 命令数・占有率・帯域

**命令数が意味を持つのは「レジスタが同じなら」という条件付きである。** ある書き換えは命令を
20.7% 減らして **38% 遅くなった**。レジスタが上限に張り付き、そこへ収めるための再計算が、
削った命令より高くついたからである。

もっと一般に、sm_60 向けの Q4_1 HFMA2 GEMV (パッチ 12 の「a16」カーネル) では、命令削減は
どの方向でも中立か負だった。ループ命令を **63% 削り、1 バイトも余計に動かさない**変更ですら
**−6.4%** である。算術は元からメモリレイテンシの下に隠れており、しかもその算術自体が
隠蔽材になっていた。

**占有率を語る前にレジスタ上限を当たる。** 32 スレッドのブロックでも、1 スレッドが
94〜140 レジスタ使うなら、SM に載るのは 32 ブロックではない。P100 の SM に載るのは
2048 スレッドではなく約 640 である。スレッド上限とブロック上限だけから 4.2 倍を予測して、
実測は 1.75 倍だった。

**占有率の変更はレジスタの変更と交絡する。** `__launch_bounds__` で占有率を 25% → 31% に
上げると −4.8% だった。しかし、結果として 96 レジスタになったコードを**元のブロック数に
戻しても回復しなかった**。損失の正体は占有率ではなく、レジスタ上限が強制したアドレス計算の
rematerialize (+30 命令) だった。

**帯域は仮定せず導出する。** 1 forward あたりに実際に読む重みのバイト数を実測時間で割り、
**実測した**天井と比べる (P100 で 606 GB/s。理論値 732 GB/s の 83%)。

## 隔離したマイクロベンチは、このカーネルを予測しなかった

実形状で実カーネルの実測時間を再現できるマイクロベンチが、実機での変化を 2 回続けて
10 ポイント規模で外した。

| 変更 | マイクロベンチ | 実機 |
|---|---:|---:|
| 一律 rows-per-block 4 → 8 | +30〜40% | −3.0% |
| 同、行数の多いテンソルのみ | +6.8% | −0.9% |

2 回目は本物の算術を入れ、4096 行で較正したうえでの失敗である。原因は特定していない
(候補は、直前のカーネルが残す L2 の状態、K の違い、他カーネルとのキャッシュ干渉あたり)。

マイクロベンチは**1 つのカーネルの変種を隔離して順位づけるには信頼できた**が、
**end-to-end の変化を予測するには信頼できなかった**。証拠ではなくフィルタとして扱うこと。

## 融合には固有の罠がある

**融合する前に、生成側と消費側の grid を比べる。** `quantize_q8_1` (grid 16) を
`rms_norm_f32<1024>` (grid 1) に畳み込むと、同じ仕事を 1/16 の並列度で回すことになる。
仕事は増えていないのに +1.90 µs 膨らみ、実測 −1.12% で棄却した。

**テンプレート引数を 1 つ増やすと、その経路を使わない呼び出しまで遅くなる。** 同じ試みで、
無関係な経路の全 14,102 呼び出しに +0.26 µs が乗った。

**カーネル引数の構造体を実行時の添字で引くと、ローカルメモリへ落ちる。**
`p.cx[blockIdx.y]` は 128 B の stack frame を作り、24,576 スレッドで 3 MB の余計な
トラフィックになって、「融合したほう」が融合しない 2 発 (14.7 µs) に対して**2.6 倍遅い
38.7 µs** になった。`#pragma unroll` で定数添字だけにすると stack frame は 0 B、
14.7 → 8.2 µs になる。`blockIdx.y` を `int` のローカル変数に受けてから比較するのも、修正の
一部である。

**`ggml_view_*` はグラフのノードとして並ぶ。** トレース上で隣接して見えるカーネルの間にも
VIEW ノードが挟まっていることがあり、「op が同じノードが連続している箇所」で集めると
**一度も発火しない**。no-op のノードは明示的に読み飛ばすこと。発火の確認はプロファイルの
カーネル名で行う。`llama-batched-bench` では CUDA バックエンドの `GGML_LOG_INFO` が
出ないためである。

**読みを遅らせると、「読む時点」も動く。** 間にソースを書くノードがいれば、融合版は新しい値を
読むことになる。これは机上の話ではない。`build_rs` は同じ状態バッファへの書き込みを
組み立てる。

**バッファ配置が融合の判断を変える。** `ggml_cuda_check_fusion_memory_ranges` は実アドレスで
判定するので、確保の位置を動かすだけの変更でも発火する融合が変わり、出力が変わる。どちらの
結果も正しいがビット一致ではなくなり、ハッシュによる回帰検出に引っかかる。

## 1 回通っただけでは証拠にならない

いずれも安価で、いずれも今回このパッチ群で実際にバグを捕まえた 3 つの習慣である。

**落ちたケースだけでなく、全体を回す。** `test-backend-ops` の SOFT_MAX の失敗は
`-o SOFT_MAX` では再現せず、フルランでしか出なかった。壊していたのが、前のほうの op が
残した状態だったからである。落ちたケースに絞り込むのはデバッグの自然な動きだが、この種の
バグはそれで見えなくなる。

**複数回回し、「どこで」落ちたかを読む。** 連続したフルランは、それぞれ別の op で、誤差の桁も
まったく違う形で落ちた (SOFT_MAX で 2e-4、MUL_MAT_ID で 0.54)。精度の問題なら、安定して同じ
op に出る。落ちる場所が動き、しかも丸めでは説明できない誤差が出るなら、それは演算ではなく
メモリの使い回しである。

**クラッシュは誤答を隠す。** 途中の abort でスイートの残りが走らず、abort を消して初めて、
その裏にずっと居たサイレントな誤結果のバグが出てきた。「落ちなくなった」は「正しい」では
ない。合格が意味を持つのは、完走が繰り返し再現してからである。

## ヒット数で線形に外挿してはいけない

グラフ再利用は、外挿すると大きな勝ちに見えた。1000 回中 341 ヒットで +1.92% だったので、
再利用率を 88% まで上げて増える約 540 ヒットぶんも、同程度になるはずだった。

実際は **+0.21%** だった。**真のヒット**は build / reset / split / alloc を全部飛ばすが、
枠を増やして得られた**部分ヒット**は build しか飛ばさない。1 ヒットあたりの価値が **15 倍**
違う。ヒットは等価ではない。1 つ 1 つが実際に何を飛ばしているのかを確認すること。
