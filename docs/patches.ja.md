# パッチ一覧

English: [patches.md](patches.md)

29 本のパッチ。以下は適用範囲ごとに章立てしてあり、適用順はファイル名の番号である。
**順序には意味がある。** 複数のパッチが同じファイルに触り、後のものが前のものの上に
成り立っている。29 本すべてを llama.cpp `v0.4.0` に対して生成しており、fuzz 0・
オフセット 0 で適用できる（現在の `llamaCppTag` は [patches.nix](../nix/patches.nix)
とトップレベル README を参照）。

各パッチの根拠は、それを裏づける実測値と**試したうえで棄却した代案**を含めて、パッチが
ソースに追加するコメントに全部書いてある。このページはその索引である。

**適用範囲**は、そのパッチで得をするのが誰かの分類である:

| 範囲 | 意味 |
|---|---|
| `sm_60` | Pascal GP100 に限定 (DP4A が無く、HFMA2 がフルレート)。他では測らずに使わないこと |
| `pre-Volta` | Volta より前の NVIDIA、すなわち Pascal 以前に限定 |
| `pre-Turing` | Turing より前の NVIDIA に限定。**Volta を含むが、Volta は tensor core を持つうえ未実測である** |
| `all archs` | アーキテクチャで分岐していないので全 GPU に影響する。実測は sm_60 のみ |
| `CUDA` | アーキテクチャ非依存の CUDA 改善 |
| `CUDA (delta-net)` | アーキテクチャ非依存だが、gated delta-net を持つモデルでしか発火しない |
| `host` | CPU 側。GPU が速いほど比率が上がる |
| `model` | ハードウェアではなくモデルアーキテクチャに依存する |

明記がない限り、出力は無パッチ版と**ビット一致**する。

## Pascal 固有

### 01 · `vmad-dp4a-sm60` — `sm_60`

sm_60 は DP4A を持たないので、upstream は 4×int8 の内積をバイト取り出しと乗算で
エミュレートしている。PTX の `vmad` (byte-selector 付きの scalar MAC) を 4 段つなげば
取り出しが不要になり、約 15 SASS 命令が約 6.75 命令になる。

**decode +6.5〜6.8%**。数値は完全に一致する。

### 02 · `mmvq-rows-per-block-sm60` — `pre-Turing`

MMVQ は出力 1 行あたり 1 ブロックなので、q8_1 の活性化行を出力行の数だけ L2 から
読み直している。pre-Turing の NVIDIA では、DRAM 帯域 (ピークの 32〜34%) でも命令数でもなく
**このロード**が律速である。

ncols_dst 1 での掃引 (9B Q4_0、`llama-bench` tg32): 1 → 46.9、2 → 54.1、
**4 → 57.7 (+23.0%)**、8 → 57.2 t/s。

**+23.0% は、採用値である 4 をこの掃引で測った値である。** 2 行だった旧版は end-to-end で
+15.4% (Q4_0) / +16.5% (Q4_1) だった。+23.0% のほうは `llama-bench tg32` の値であり、
このハーネスには投機デコードが無い ([benchmarking.ja.md](benchmarking.ja.md) を参照)。
Turing 以降と GCN は upstream の値のままである。

### 05 · `mmvf-f32-pascal` — `pre-Turing`

`mmvf.cu` は pre-Turing の NVIDIA で F32 のベクトル経路を `ne11 <= 3` に制限しているが、
この 3 は**行列演算ユニットを持つ** GPU 向けの値である。この関数にある他の
「行列演算ユニット無し」の分岐はすべて 8 を返しており、呼び出し側のコメントも
「tensor core が無い GPU ではベクトルカーネルが有利」と書いている。Pascal は行列演算
ユニットを 1 つも持たない。

投機デコードでは `ne11 = n_draft + 1 = 4` になって上限を 1 つ超えるため、F32 の `mul_mat` が
すべて cuBLAS の SGEMM に落ちていた (decode の GPU 時間の 5.9%)。

**ワークロードにより +3.7〜4.3%**。3 回独立に再現している。出力を確認した 1 つの
ワークロードではビット一致した (しかも 3.6% 速い) が、他は未確認である。編集対象の分岐は
`cc < TURING` なので Volta にも掛かるが、Volta は未実測である。

### 07 · `mmvq-moe-rows-sm60` — `all archs`

融合 MoE matvec の起動側にある `rows_per_block = 2; // 2 gives best perf based on tuning`
はハードコードされたアーキテクチャ非依存の値であり、そのチューニングは DP4A の無い環境では
行われていない。このカーネルは MoE の 1 decode ステップの 20.1% を占める。

**decode +1.9%**。prefill は変化なし (MMQ を通るため)。

**このパッチはアーキテクチャで分岐していない。** ただの `constexpr` なので全 GPU が 4 に
なり、upstream の 2 はどこにも残らない。実測は sm_60 のみである。Turing 以降で使うなら、
測るか元に戻すこと。

### 08 · `mmvq-mmid-batch-sm60` — `pre-Volta`

量子化された `MUL_MAT_ID` を融合 MoE matvec に回す条件の表は `cc < VOLTA` で一括して
いるため、sm_60 と sm_61 が同じ扱いになる。この 2 つは「上限を超えたときのフォールバック先が
妥当かどうか」という一点で決定的に違う。sm_61 は MMQ に落ちれば済むが、sm_60 は
sorted-gather まで落ちる。

**+2.2%** (3 プロンプトの幾何平均。退行するワークロードは無し)。

パッチ自身が書いている注意点を 2 つ、ここでも挙げておく。1 つは、直接測ったのは IQ2_XS と
IQ3_XXS だけだということである。表全体を引き上げているのは、その理由 (sm_60 では
フォールバック先がどの型でも遅い) が型に依存しないからであって、実測したからではない。
これは論証であって測定ではなく、このパッチで最も弱い部分である。もう 1 つは、表が
`cc < VOLTA` で一括なので **sm_61 (P40 / GTX 10xx) でも上限が外れる**ことである。
sm_61 のフォールバック先は MMQ なので、上の論証は当てはまらない。

### 09 · `mmvq-nwarps-small-k-sm60` — `pre-Turing`

ブロックは K に関係なく 4 ワープ幅だが、スレッドが K のループに入るのは
`tid/(qi/vdr) < ncols_x/qk` のときだけである。K が小さいとブロックの後半がカーネル全体を
通じて遊ぶ (K=512 の IQ3_XXS では 128 スレッド中 16 スレッドしか動いていなかった)。

ホスト側から「K を覆うのに必要な最小ワープ数」を渡すようにすると、IQ3_XXS が
64.03 → 36.64 µs、Q3_K が 106.59 → 48.27、IQ2_XS が 24.00 → 20.76 になる。

**MoE decode +1.29%。dense はノイズ内で不変 (+0.12%、ノイズ下限 ±0.17%)**。
`rows_per_block` を上げても直らない。行は同じスレッドが内側のループで回すので、遊休
スレッドは遊休のままである。

インスタンス化してあるのは 1・2・4 ワープだけなので、K が 4 ワープ中 3 ワープ分を要する
場合は 2 ワープになり、各スレッドが 1 項ではなく 2 項を累算する。積の集合は同じで順序だけが
変わるため結果は正しいが、そこでは**ビット一致しない** (Q4_0 なら `ncols_x` が 1056〜1536。
`blocks_per_iter_1warp` が 16 なので `need` が 3 になるのは 33 ブロックから。1024 は
32 ブロックで、2 ワープがちょうど覆うためビット一致は保たれる)。
`need` が 1 または 2 のときは落ちたワープの寄与が厳密に `+0.0f` で、レーンごとの項の集合も
変わらないのでビット一致は保たれる。判定は `need` であって起動ワープ数ではない
(`need` が 2 でも 3 でも起動は 2 ワープである)。

### 12 · `mmvq-f16-sm60` — `sm_60`

HFMA2 で組んだ Q4_1 GEMV。この中で最大のパッチである。GP100 では発行スロットあたりの
MAC 数が HFMA2 で VMAD の 4 倍になるので、ニブルを LOP3 のマジック定数だけで `half2` に
展開し (整数から浮動小数への変換命令をどこにも入れずに)、fp16 で積む。

初版で**幅 5 で +9.4%**、改訂版で **end-to-end +9.5%** だった。改訂版では、形状に応じた
ワープ数の選択と、20 バイトの `block_q4_1` が撒いていた行あたり 64bit 乗算の除去を行って
いる。数値としてはノイズ内で同値だが、より多くのワークロードで確認している。

この経路を通る幅では、出力の最下位ビットが変わる (エピローグの変換を 2 回から 1 回に
減らしたため)。ubatch 4 の perplexity は 7.2370 → 7.2359 (−0.015%) と動いた。これは
スループット測定の ±2.9% の 200 分の 1 でしかないので、無害性を確認したのではなく
**上限を与えている**にすぎない。無害である根拠は、上記の脱量子化が厳密であること
(Sterbenz) の側にある。

ノブ: `GGML_A16_NCOLS_MIN` / `GGML_A16_NCOLS_MAX` で対象の幅を絞れば、同一バイナリ内で
upstream のカーネルと比較できる。`GGML_A16_NWARPS` / `GGML_A16_QVEC` /
`GGML_A16_SMALL_GRID` は自動選択の上書きである。

### 31 · `fattn-f16-kv-chunk` — `pre-Turing`

tile 版 flash-attention カーネル (tensor core が無いときの経路) は K / V を F16 で読むので、
KV cache が量子化されていると `launch_fattn` はまず cache 全体を F16 に変換した作業領域を
作る。ggml-alloc はその作業領域をグラフ予約時に**最大文脈**でサイズ決めする。KV の 1 列
あたり 1 トークン 4 バイト、4 ヘッド × 256 の KV なら 4 KiB/token で、ctx 81,920 で 320 MiB、
262,144 で 1,024 MiB を、文脈を使っていようがいまいが KV cache の上に払い続ける。

このパッチは 16,384 トークンずつ変換し、チャンクごとにカーネルを走らせ (parallel block を
2 以上にして正規化前の部分和と (max, sum) を書かせる)、online-softmax のマージカーネルで
累算器に畳み込む。作業領域はチャンク分の 64 MiB で頭打ちになる。
`GGML_CUDA_FA_F16_KV_CHUNK` でチャンク (トークン数、256 の倍数に切り上げ) を変えられ、
`0` でチャンク化を止められる。

27B モデル (64 層、うち full attention 16 層、q4_0 KV、ubatch 128、`LLAMA_DEC_SLOTS=0`)
での CUDA0 計算バッファ:

| ctx | 前 | 後 |
|---:|---:|---:|
| 81,920 | 360 MiB | 104 MiB |
| 262,144 | 1,152 MiB | 192 MiB |

ctx 81,920・全層 GPU での回帰確認: prefill 11k 101.0 → 101.1、40k 90.6 → 88.6、
66k 82.6 → 81.3 t/s。decode 20.46 → 20.39、14.78 → 14.68、12.42 → 12.36 t/s。
VRAM ピークは 14,043 → 13,787 MiB で、深さと生成量を散らした 8 要求を通して一定。
深い prefill は起動が増えるぶん 2% ほど落ちる (210k では ubatch ごとに 13 チャンク × 16 層)。
decode は vec カーネルを通るので手つかず。

ctx 262,144 で 960 MiB が買うもの: それまでモデルを収めるのに SSM ブロック 48 本のうち
14 本 (各 170 MiB) を CPU に置く必要があったのが、8 本で済む。decode 11k 8.36 → 11.04、
40k 7.47 → 9.54、210k 4.33 → 4.93 t/s。210k の prefill 52.2 → 53.0 t/s。ピーク 15,629 →
15,687 MiB で空き 582 MiB。

`test-backend-ops -o FLASH_ATTN_EXT` は `GGML_CUDA_FA_F16_KV_CHUNK=256` (量子化 KV ×
prefill 幅のバッチ 290 件がチャンク経路を通る) でも既定でも 2,938/2,938 通る。KV が
チャンクより長いときは softmax の合算順が変わるので**ビット一致しない**。チャンク以下では
元のコード経路そのままなのでビット一致する。mma カーネル (Turing 以降) は stream-k なので
対象外で、作業領域は従来の最大サイズのまま。

棄却した案: 変換先を計算バッファではなくプールから取る。固定費が「使っている深さに比例する費用」に
変わるだけで、VMM プールは縮まないので天井は同じになる。

README の 2 モデルでの退行確認は [benchmarking.ja.md](benchmarking.ja.md) の作法どおり
(同一バイナリで `GGML_CUDA_FA_F16_KV_CHUNK=0` を off 腕、30 本適用ビルドを対照腕、交互、
後半は順序反転、毎回 58 °C 以下まで冷却、4 ラウンドで初回は捨てる)。README 条件
(`-ngl 56 -fa 1`、F16 KV) では変換自体が走らず、3 腕は 0.1% 以内で一致する。q4_0 KV・
深さ 24k ではチャンク化した prefill が pp512 で 0.54% (9B) / 0.30% (35B-A3B) の費用になる。
decode は不変 (vec カーネル)。MoE で prefill テストの後に decode テストを同一プロセスで
回したときだけ出た −1.2% は、`GGML_CUDA_DISABLE_FUSION=1` でも tg 単独の実行でも消えた。
benchmarking.ja.md に書いた配置依存の融合判定であって、カーネルの性質ではない。

## アーキテクチャ非依存の CUDA

### 04 · `concat-non-cont-flat` — `CUDA`

非連続 concat のカーネルは 1 ブロックを `(i1, i2, i3)` に割り当て、`i0` を `blockDim.x` で
回すので、`min(ne0, 256)` 本しかスレッドが働かない。delta-net の conv 状態の concat は
`ne0 = 4..8` に対して `ne1 = 8192` なので、**32k 要素のコピーに 210 万スレッド**を起動し、
128 KiB に 33 µs (732 GB/s のカードで 4 GB/s) かかっていた。

1 スレッドが 1 出力要素を担当する形に平坦化して **18.0 → 4.7 µs**。decode の GPU 時間の
1.8% にあたる。

### 10 · `mmvq-q8-1-activation-cache` — `CUDA`

`ggml_cuda_mul_mat_vec_q` は呼び出しごとに `src1` を量子化し直すので、FFN の gate と up が
同じ活性化を 2 回量子化する。`quantize_row_q8_1_cuda` は `src0->type` を無視するため、
2 回目の結果は 1 回目とバイト一致する。量子化の起動のうち 34.6% が重複だった。

初回の計測で **MoE decode +1.17% / dense +0.88%**。ただし、ここで配布している形はその値より
約 0.5% 遅い。理由は次の 2 つで、どちらも省略できない。

**バッファを CUDA プールから取ってはならない。** プールはスタックアロケータで、解放が必ず
末尾であることを assert する。したがって確保を呼び出しをまたいで保持すると、mmvq の前に
確保して後に解放する呼び出し元が現れた瞬間に壊れる。`ggml_cuda_mul_mat_id` の
sorted-gather 経路がまさにそれである。代わりに、伸長のみを行う生の device 確保にしてある。
プールのアリーナから外すとアドレス配置が変わり、`ggml_cuda_check_fusion_memory_ranges` は
融合の可否を**実アドレス**で決めるので、約 0.5% の大半はそこで消えている。

**キーはテンソルのポインタだけでなく `src1->data` を含まなければならない。** 同じ
sorted-gather 経路は `ggml_tensor` をループ**内**で宣言するため、全 expert が同じスタック
アドレスを使い回し、`data` だけが進む。ポインタだけをキーにすると、トークン数が同じ 2 つの
expert が誤って一致してしまい、後の expert が**前の expert の活性化で計算される**。

共有バッファは、それを所有するストリームでしか安全に使えない。したがって他のストリームからの
呼び出しは、upstream どおりの呼び出しごとのプール確保に落とす。

これに代えて upstream の MMVQ 融合を Pascal で有効化する案は **−0.48% で棄却した**
(この比較はパッチではなく、ここに記録してある)。融合でも同じ重複は消えるが、2 つの重みを
1 カーネルに持つのでレジスタが増え (Q3_K で 140 → 218)、占有率が 36% 落ちる。upstream の
「fusion is not universally faster on Pascal」はここでも成り立っており、このパッチは効く
半分だけを取っている。

### 14 · `getrows-narrow-rows` — `CUDA`

`get_rows` は gather する 1 行につき 256 スレッドのブロックを 1 つ起動する。`ne00 = 1` では
248,320 個のブロックが 1 要素ずつ運ぶ形になり、278 µs かかる。`(row, element)` を 1 次元に
潰せば 970 ブロックで済む。

### 16 · `cpy-fastdiv` — `CUDA`

`cpy_scalar` は 1 要素あたり 64bit の整数除算を 6 回行う。マイクロベンチの形状
(24,576 要素の f32 コピー) で 4.94 µs であり、これは同じ形状の自明なカーネルの 2.6 倍、
40 GB/s は実測 read 帯域の 1/15 である。除数はループ不変なので、ggml が既に持っている
`fastdiv` で置き換えられる。

**1 呼び出しあたり 11.26 → 4.96 µs (−56%)**、end-to-end +0.82%。

### 17 · `norm-register-cache` — `CUDA`

`rms_norm_f32` / `l2_norm_f32` は `x` を 2 回読む (二乗和の計算とスケールの適用)。単トークンの
decode では `grid = (1,1)`、つまり 56 SM のうち 1 個しか使わず、1 発 7.79 µs、decode の
1.9% になる。行をレジスタに持てば 2 回目の読みが消える。

**`rms_norm<1024>` が 7.79 → 6.50 µs、`l2_norm<32>` が 2.96 → 2.39 µs**、
end-to-end +0.71% (dense) / +0.95% (MoE)。

`rms_norm` 側は `block_size >= 1024` のコンパイル時ゲートで切り分ける。`l2_norm` 側は
ブロックサイズによらずキャッシュする。実行時ゲートでは負ける。起動下限が 1.9 µs の
カーネルでは、分岐のぶんの命令がそのまま約 6% の**コスト**として出る。

### 18 · `fuse-sibling-nodes` — `CUDA`

同形のノードが連続している箇所を 1 発にまとめる。topk-moe や rope+set_rows と違って
**ノードを 1 つも消さない**ので、必要な条件は「並び順を入れ替えても結果が変わらないこと」
だけであり、これをバイト範囲で実行時に確認する。

対象は連続する `CPY` (2.60 µs × 5 発 → 8.46 µs × 1 発) と `L2_NORM`
(2.26 × 2 → 3.51 × 1)。**+1.06%**、出力はビット一致する。

停止スイッチ: `GGML_CUDA_DISABLE_FUSE_CPY` / `GGML_CUDA_DISABLE_FUSE_L2_NORM`。
`GGML_CUDA_FUSE_LOG=1` で発火した規則を、`=2` で発火しなかった理由を出力する。

### 19 · `fuse-pre-add-rms-norm` — `CUDA`

upstream の融合は `rms_norm` の**後段**だけで、前段の残差加算は素通りしていた。
`add → rms_norm` は隣接ペアの中で最大で、decode の GPU 時間の 3.11% を占める。`rms_norm` は
1 行 1 ブロックなので、加算はそのプロローグで済ませられる。

`k_bin_bcast` が 5,514 → 1,872 発になり、代わりに `rms_norm_f32<1024>` が 6.53 → 8.19 µs に
なる。差し引き **+0.70%**、出力はビット一致する（dense モデルで計測）。

**v0.4.0 リベース以降は既定オフ。** 理由と、有効化（`GGML_CUDA_FUSE_PRE_ADD=1`）が
何を保証し何を保証しないかは、パッチ 20 の後のハザード説明を参照。

### 20 · `fuse-add-unary-mul` — `CUDA`

`mul(unary(add(x, bias)), scale)` を 1 発にする。upstream の UNARY+MUL 融合は
`ggml_are_same_shape` を要求するので `n_tokens > 1` で外れ、前段の ADD は常に素通りする。

`k_bin_bcast` が 1,872 → **0 発**、カーネル総数が 54,326 → 52,454。**+0.72%**、出力は
ビット一致する。19 と同様に既定オフ（後述）。

**既知のハザード。19・20 とも `ggml_cuda_check_fusion_memory_ranges` を通しておらず、
どちらもオプトイン。** どちらの融合も無融合版には無い書き込み（ADD の `dst`）を追加し、
同一カーネル内でプロローグが前段の入力（19 なら `add->src[0]`/`src[1]`、20 なら
バイアス加算の入力）を読み、エピローグが `MUL` ノードの出力を書く。`add->src[*]`（19）は
ADD の時点で寿命が尽きるため、ggml-alloc がその解放済みブロックから `MUL` の出力を
切り出すと、同じブロックの一部を共有する別の割り当てで、あるエピローグの書き込みが
**別の**呼び出しのプロローグがまだ読もうとしている領域に重なりうる ——これは upstream
の検査が本来弾く部分重なりである（未融合なら 3 カーネルが直列に走るので安全）。
`v0.2.0` では顕在化せず、`v0.4.0` の MoE グラフで非決定的な decode 出力として表面化した
（同一 seed で 3 回実行し 3 回とも別出力）。融合カーネル自体は単体では正しい。

最初に試した修正は、グラフに `MUL_MAT_ID`（＝MoE）が含まれる場合に 19 をスキップする
ガードだった。これは不十分だと分かった: `ggml_backend_sched` はグラフをバックエンドで
分割でき（`--n-cpu-moe`、`-ot "exps=CPU"`）、CPU split に回された `MUL_MAT_ID` は CUDA
側からグラフを見ても見えないため、ガードは実際には MoE のグラフを「dense」と誤判定する。
20 はそもそもこのガードを持たず、非決定性が実際に観測されたアーキテクチャ（gated
delta-net のゲート前処理）そのものに同じ read-under-write の形で発火する。これを踏まえ、
両方とも**既定オフ**にした（有効化は `GGML_CUDA_FUSE_PRE_ADD=1` /
`GGML_CUDA_FUSE_ADD_UNARY_MUL=1`）——dense モデルではビット一致することは実測済みだが、
スケジューラがグラフを分割しうる状況で安全であることは保証されない。根本対処は
per-patch のワークアラウンドではなく upstream 側のメモリレンジ検査に委譲すべきもので
ある。なお `ggml_cuda_check_fusion_memory_ranges` 自体は連続した `(node_idx,
node_count)` しか受け付けない一方、`ggml_cuda_collect_ops` は非連続な `idxs` を返し
うるため、この検査をそのまま呼ぶだけでは閉じない。

有効化スイッチ（既定オフ。他パッチの停止スイッチとは逆）:
`GGML_CUDA_FUSE_PRE_ADD=1`（19）、`GGML_CUDA_FUSE_ADD_UNARY_MUL=1`（20）。

### 26 · `cpy-fused-rows` — `CUDA`

融合したコピーを、1 スレッド 1 要素から **1 スレッド 1 行**に変える (dim0 が連続で、上位
次元が密なとき)。添字計算が 1 要素あたり `fastdiv` 6 回から、1 行あたり乗算 1 回になる。

実形状での単体ベンチ (4 変種):

| | µs | GB/s |
|---|---:|---:|
| 1 スレッド 1 要素 (現行) | 8.92 | 110 |
| 1 スレッド 1 行、`ne0` は実行時の値 | 5.42 | 181 |
| 1 スレッド 1 行、`ne0` はコンパイル時定数 | **4.66** | **211** |
| 添字計算なし (上限) | 4.17 | 236 |

配布しているコードは、可能なら 3 行目の経路を通る。これが **1.9 倍**である。
**律速はデータ量ではなく添字計算**であり、上限まではあと 12% しかない。
停止スイッチ: `GGML_CUDA_DISABLE_CPY_ROWS`。

### 28 · `top-k-partial` — `CUDA`

`ggml_top_k` は `cub::DeviceTopK::MaxPairs` を使うが、これは **CCCL 3.2 以上を要求する**。
CCCL 3.x は CUDA 13 に同梱されるので、**CUDA 12.x のどのリリースでも**条件が成立せず、
`argsort_f32_i32_cuda_cub` にフォールバックして、**語彙を完全に基数ソートして先頭 k 個を
取る**動作になる。投機デコードではこれが k=10・語彙 151,936 で毎トークン走り、約 172 µs、
decode の 1.1% になる。

代わりに 2 段の部分選択を行う。比較は cub と同じ単調な uint32 写像で行い、key を上位 32bit、
`~idx` を下位 32bit に詰めるので、**単純な符号なし比較だけ**で cub の stable な順序を
±0 や NaN まで再現できる。結果はビット一致する。

単体ベンチ (n=151,936): cub の全ソートが 157.2 µs に対して **k=10 で 20.6 µs (7.6 倍)**、
全ソートとの不一致は 0 件。

速くするのに効いたのは次の 2 つで、どちらも実測で判明した。1 つはブロック全体のツリー
リダクションを warp shuffle に置き換えたこと (70.9 → 42.1 µs。k ラウンドぶんの barrier が
律速だった)、もう 1 つは 64bit に詰めて分岐のない shuffle 1 本にしたこと (42.1 → 20.6) で
ある。1 スレッドの受け持ち要素数はほぼ無関係だった。作業量ではなく、ラウンドごとの
レイテンシが律速である。

k > 16 (候補をスレッドのレジスタ配列に置く実装上の上限) の場合、行が短い場合、グリッドが
大きすぎる場合は、従来のソート経路に落とす。
停止スイッチ: `GGML_CUDA_DISABLE_TOP_K_PARTIAL`。

CUDA 専用: このブロック全体を `#if !defined(GGML_USE_HIP)` で囲んでいる。理由は 2 つ。
ここで使う `__shfl_xor_sync` は cub の 3 引数形だが、`ggml-cuda/vendors/hip.h` はこれを
4 引数マクロとして `#define` しているため、書いたままでは HIP でコンパイルが通らない。
さらにコンパイルが通ったとしても、カーネルは `CUDA_TOP_K_WARPS`・`threadIdx.x & 31`/`>> 5`・
`e*32` と全体を通じて 32 レーン warp を前提にしており、AMD の 64 レーン wavefront では
成立しない。`v0.4.0` 以降 upstream 自身も CUB 不在時の HIP 専用フォールバック
`top_k_radix_cuda` (`!GGML_CUDA_USE_CUB && GGML_USE_HIP` かつ `ncols > 1024`) を持っており、
このパッチは HIP 側ではその経路と、`ncols = 1024` 以下での全ソートを一切変更しない。

> これは Pascal 以外にも効く。**CUDA 12.x で GPU サンプリングを使っている人は全員、
> 毎トークン語彙全体のソートを払っている。**

### 29 · `mmvq-iq3xxs-grid-smem` — `CUDA`

`vec_dot_iq3_xxs_q8_1` は重み 4 個ごとに `iq3xxs_grid` を 1 回引く。ワープ 32 レーンの
添字は互いに無関係なので、1 命令のロードが相異なるアドレスの数だけセクタに分解され、
直列に再発行される。**命令数を数えるとこれは見えない**。ロードはループ本体約 946 命令の
うち数命令でしかないので、命令数からは数 % と見積もられるが、実測は 4 割である。

1 KiB のテーブルをカーネル先頭で共有メモリに載せるだけで消える。

単独 GEMV (K=5120 / N=17408、引き方だけを差し替え、µs/Mweight):

| grid の置き場所 | nc=1 | nc=2 | nc=3 |
|---|---:|---:|---:|
| global (上流) | 2.965 | 4.103 | 5.204 |
| `__constant__` | 6.486 | 6.484 | 6.516 |
| **共有メモリ** | **1.824** | **2.972** | **4.000** |
| 添字を一様化 (対照・値は壊れる) | 1.842 | 2.944 | 4.013 |

共有メモリは対照に到達する。つまりテーブル引きのコストは「減る」のではなく**ゼロになる**。
`__constant__` は上流より 2.2 倍**遅い**。定数キャッシュは 1 サイクル 1 アドレスの
ブロードキャストしかできず、発散すると 32 回直列化するためである。

IQ3_XXS が重みの 27% を占める 27B dense モデル、MTP 投機デコード有効、サンプラーは
greedy（温度 0 / top-k 1）での実測:

| プロンプト | 上流 | パッチ後 | |
|---|---:|---:|---:|
| 短 (256 トークン生成・2 周) | 27.03 / 27.04 | 29.08 / 29.10 | **+7.6%** |
| 33k トークン | 18.70 | 19.80 | **+5.9%** |
| 60k トークン | 15.51 | 15.99 | **+3.1%** |

文脈が長いほど効きが薄まるのは、attention と KV→f16 展開の比重が上がって
`mul_mat_vec_q` の取り分が下がるためである。

**出力は全点でビット一致**である。生成テキストのハッシュ・受理ドラフト数・パス数がすべて
同一なので、受理率の項が比較に混入しない。ピーク VRAM も MiB 単位で変わらない。

grid のアドレス計算が消えるぶんレジスタも減る (`nc=1` のカーネルで 94 → 80)。
共有メモリはブロックあたりちょうど 1024 バイト増える。

`iq3xxs_grid_smem_init()` は `__syncthreads()` を含むので、**早期 return より前**で
呼ばなければならない。

同じ発散したテーブル引きは、MMVQ の `iq2xxs_grid` / `iq2xs_grid` / `iq2s_grid` /
`iq3s_grid` / `iq1s_grid_gpu` にもある。ここでは触っていない。これらのテーブルは
2 KiB から 8 KiB あり、共有メモリに載せたときの占有率との釣り合いが本パッチとは
別物になるからである。MMQ も `load_tiles_iq3_xxs` で**この 1 KiB の同じテーブル**を
引いているが、そちらも触っていない。

`mul_mat_vec_q_moe` にも同じ初期化を入れてあるのは `vec_dot` を共有しているためである。
このカーネルは MoE の `MUL_MAT_ID` で 2 トークン以上のときしか走らず、dense モデルでは
到達しないので、単独で測った。IQ3_XXS がバイトの 31.7% を占める 35B-A3B MoE を 28 本
適用版と比べ、順序を反転した 2 周で 100.40 / 101.27 → 101.83 / 102.00 t/s。
MTP 投機デコードは有効で (ドラフト 148 本中 124 本が受理、検証幅 2.12)、
**そもそもこれが `MUL_MAT_ID` に 2 トークン以上を流してこのカーネルに到達させている。**
4 本ともハッシュ・受理数・パス数が一致しているので、ここでも受理率の項は混入しない。
VRAM も不変である。ただし +1.1% は上の dense の値に比べて効果量がずっと小さいので、
**目安**として読むこと。確実に言えるのは、追加したバリアと 1 KiB の fill が
この経路で測れるほどのコストにならないことである。

### 30 · `mmvq-ksigns-smem` — `CUDA`

IQ2_XXS / IQ2_XS / IQ3_XXS の `vec_dot` は、詰め込まれた 7bit の符号フィールドから
バイトごとのマスクを 2 本作り、それを適用する。

```c
const uint32_t signs = unpack_ksigns(aux32 >> (7*l0/2));   // s * 0x01010101
const int signs0 = __vcmpne4(signs & 0x08040201, 0);
const int grid_l = __vsub4(grid_pos.x ^ signs0, signs0);
```

この経路は sm_60 では全段がエミュレーションになる。バイト単位の SIMD 比較も SIMD 減算も
無いので `__vcmpne4` と `__vsub4` はどちらも複数の `LOP3`/`LOP32I` に展開され、
`s * 0x01010101` の byte broadcast は 32bit 整数乗算、すなわち `XMAD` 3 本になる。
IQ3_XXS のループ本体は重み 32 個あたり `LOP32I` 120 本と `LOP3` 112 本で、
そのほとんどがこれである。

符号適用を丸ごと削ると（数値は壊れるが上限を見るための対照）、K=5120 / N=17408 /
`nc=1` の単独 GEMV で **−30.4%**。パッチ 29 の後にこのカーネルに残っていた項目の中で
最大であり、grid の共有メモリ引き（12.5%）、dp4a エミュレーション（8.1%）、
活性化ロード（4.1%）より大きい。

マスクは元の 7bit だけで決まるので、ブロックごとに 1 回だけ埋める 128 エントリの表で
この連鎖全体を共有メモリ 1 回のロードに置き換えられる。表が小さく、適用が安いのは
次の 2 点による。

- 8 番目の符号は残り 7 個のパリティなので 128 エントリで足りる。上流が切り捨てるバイトに
  混じるゴミビットも、上流と同じ理屈で打ち消える
- `iq2xxs_grid` / `iq2xs_grid` / `iq3xxs_grid` のバイトは全て 4 以上なので、
  バイトごとの `(g ^ 0xff) + 1` は隣のバイトへ桁上がりしない。よって `__vsub4` は
  素の 32bit 加算で置き換えられる

見た目以上にレイアウトが効く。IQ3_XXS の単独 GEMV（K=5120 / N=17408）で 3 通り測った。
いずれも出力は上流とビット一致する。

| 表のレイアウト | `nc=1` | `nc=2` | `nc=3` |
|---|---:|---:|---:|
| 上流 | 149.5 µs | 198.2 µs | 257.3 µs |
| `uint4`・128bit ロード 1 本 | 130.9 | 202.3 | 247.5 |
| `uint2`・64bit ロード 1 本 | 125.2 | 187.8 | 244.4 |
| **平坦な 256 エントリ配列から `uint32` 2 本** | **128.4** | **188.9** | **236.0** |
| 上限: 符号を適用しない（数値は壊れる） | 103.9 | 153.1 | 214.0 |

上流の連鎖を残したまま乗算だけを `__byte_perm` にしても −1.9% / −2.6% にしかならない。
つまりコストは乗算にあるのではない。

`test-backend-ops -o MUL_MAT perf`、m=4096 k=14336、両腕とも同じ flake、
順序を 2 ラウンド目で反転して交互に測定:

| type | n=1 | n=2 | n=3 | n=4 |
|---|---:|---:|---:|---:|
| IQ3_XXS | **−21.1%** | **−9.5%** | **−9.3%** | **−8.7%** |
| IQ2_XXS | −3.7% | −7.4% | −8.6% | −8.0% |
| IQ2_XS | +0.3% | −9.2% | −7.2% | −7.2% |
| IQ4_XS（対照） | −0.2% | +0.1% | −0.0% | −0.1% |

`n=1` では IQ3_XXS が 99.65 → 78.62 µs となり、IQ4_XS（78.44）と Q4_1（78.65）に並ぶ。
重み 1 個あたり 3.06bit の型が、4.25bit と 5.00bit の型と同じ時間になったということである。

IQ2_S は触っていない。この型は 7bit のフィールドではなくニブル 2 個で符号を持ち、
この表の前半がそのまま使えるのだが、通してみると `n=3` と `n=4` は速くなる一方で
`n=2` が 2 ラウンドとも 6.5% 遅くなった。

`-o MUL_MAT` 1134/1134、`-o MUL_MAT_ID` 790/790 が pass。

GPU 上の重みの 30% が IQ3_XXS である 27B dense モデル、MTP 投機デコード有効、
サンプラーは greedy（温度 0 / top-k 1。下のビット一致の確認ができるのはこのため）、
短プロンプトは 3 ラウンド、長文脈は 2 ラウンド、順序は交互:

| プロンプト | 29 まで | +30 | |
|---|---:|---:|---:|
| 短（256 トークン生成） | 28.92 / 28.90 / 28.87 t/s | 29.43 / 29.40 / 29.43 | **+1.8%** |
| 33k トークン | 19.97 / 19.86 | 19.92 / 19.98 | +0.2% |
| 60k トークン | 16.32 / 16.13 | 16.35 / 16.48 | +1.2% |

出力は全点でビット一致する。生成テキストのハッシュ、受理されたドラフト数、
パス数のいずれも同じなので、受理率の項がこの比較に入り込む余地はない。
VRAM のピークは MiB 単位で不変。ブロックあたりの共有メモリは 1KiB 増える。

エンドツーエンドの数字がカーネルの数字よりはるかに小さく、長文脈では 0.2〜1.2% に
とどまるのはパッチ 29 と同じ理由による。長文脈のパスでは attention と KV の f16 展開の取り分が
増えていく。

IQ2_XS を 47.9%、IQ3_XXS を 31.7% 持ち、`mul_mat_vec_q` ではなく
`mul_mat_vec_q_moe` を通る 35B-A3B MoE では、順序を交互にした 2 ラウンドで
101.79 / 101.83 → 103.74 / 102.83 t/s、すなわち **+1.5%**（検証パス 1 回あたり
19.05 → 18.78 ms）。4 本ともハッシュ・受理数・パス数・検証幅・VRAM が一致する。
バイトの 8 割がこの 2 型であるわりに効果量が小さいのは、トークンごとに読まれる
エキスパートが一部だけだからである。

`ksigns_smem_init()` は `__syncthreads()` を含むので、どの早期 return よりも前に
呼ばなければならない。MMQ も `load_tiles_iq2_xxs` / `load_tiles_iq2_xs` /
`load_tiles_iq3_xxs` で同じ符号表現を読むが、そちらは触っていない。

> パッチ本体より価値のある計測上の注意。この測定の最初の版は、1 ブロック 1 出力行で
> 書いた単独 GEMV を使っていた。そこでは符号経路はカーネルの 4%、表引きは 3% **遅い**
> と出た。`mul_mat_vec_q` は 1 ブロック 4 行（パッチ 02）で動いており、これによって
> カーネルの律速要因が変わる。実物に合わせて書き直すと、同じ 2 つの測定が 30% と
> 14% **速い** に変わった。実カーネルの起動形状を再現しないマイクロベンチは、
> 結果を鈍らせるだけでなく符号を反転させうる。

## delta-net / gated delta-net (Qwen3-Next / Qwen3.5)

以下はアーキテクチャ非依存の CUDA 変更だが、gated delta-net の linear attention を持つ
モデルでしか発火しない。

### 23 · `fuse-gdn-beta-sigmoid` — `CUDA`

`beta = sigmoid(x)` を `gated_delta_net` に畳み込む。`unary_op_kernel<op_sigmoid>` は
`gated_delta_net_cuda` と**同数** (4,080 発、6.86 ms) 起動されており、そのうち 4,032 発は
`grid = 1`、つまり全体が起動の固定費だった。gdn は既に `g` 側の `expf` を畳んでいる。

node-preserving (gdn が畳み込んだノードの dst も書く) なので使用回数の解析は不要であり、
結果はビット一致する。
停止スイッチ: `GGML_CUDA_DISABLE_FUSE_GDN_BETA`。

### 24 · `fuse-gdn-state-gather` — `CUDA`

SSM state の `GET_ROWS` (2 MB の gather) を `gated_delta_net` に畳み込む。
`k_get_rows_float_vec` は gdn と同数 (3,984 発、46.24 ms、decode の 1.4%) 起動されており、
中身はキャッシュから 2 MB コピーして渡すだけの往復だった。gdn は既に**新しい** state を
キャッシュへ直接書いているので、入力側も直接読ませる。

`GET_ROWS` は 10 ノード手前にあるので、**ノードの実行を後回しにして消費側に畳み込む機構**を
入れている。並行ストリームを使っている場合は順序の入れ替えが危険なので無効化する。
停止スイッチ: `GGML_CUDA_DISABLE_FUSE_GDN_GATHER`。

### 25 · `gdn-gather-single-snapshot` — `CUDA`

行番号の退避を、層ごとではなくグラフ 1 本につき 1 回にする。全 SSM 層が同じインデックス
テンソルを使うので、層ごとに退避すると DtoD コピーが 4,080 発 (+7.31 ms) 増える。

### 27 · `fuse-concat-gather` — `CUDA`

conv 状態の `GET_ROWS` を、直後の `CONCAT` に畳み込む (そのために `dim == 0` の CONCAT を
1 スレッド 1 行にする)。`build_conv_state` は 96 KB の行を gather して即 concat する往復で、
どちらのカーネルも 42 / 51 GB/s、つまり天井の 7〜8% しか出ておらず、律速は添字の割り戻し
だった (`concat_cont<T,0>` は `ne0` がたった 4 なのに **64bit の実行時除算**をしており、
GP100 には 64bit の除算器が無い)。

単体ベンチでは、2 カーネルの 7.203 µs が**融合で 2.819 µs (−61%)** になる。

**行単位化だけでは効果がゼロである** (平均 +0.006%、8 ラウンド中プラスは 3 本)。
1 スレッド 1 行が単体で得になるのは、dst の行がちょうど 16 B、つまりベクトルストア 1 発に
なるときだけである。行単位化**と融合を合わせる**と平均 +0.74%、8 ラウンド中プラス 7 本に
なる。カーネル 1 発が丸ごと消えるからである。したがって、融合しない経路は 16 B の行だけに
絞ってある。

停止スイッチ: `GGML_CUDA_DISABLE_CONCAT_ROWS` / `GGML_CUDA_DISABLE_FUSE_CONCAT_GATHER`。

## ホスト側

### 11 · `penalties-direct` — `host`

`llama_sampler_penalties_apply` は候補を 1 つずつ `unordered_map` で引くが、map の要素数は
高々 `penalty_last_n` (既定 64) で、候補リストのほうは語彙全体である。語彙 151,936 では
**候補ごとに 1 回 hash lookup して、当たるのは最大 64 件**、つまりおおよそ 2,400 回に 1 回しか
仕事をしていない。**1 トークンあたり 0.78 ms、スループットの 5.3%** にあたる。

代わりに、ペナルティ対象のトークン側を走査する。各要素について `cur_p->data[id].id == id` を
確認し (高々 64 回の比較)、1 つでも外れたら元の全走査に落とす。適用される演算とその順序は
同じなので、出力はビット一致する。

> これも Pascal 以外に効く。ホスト側の処理なので **GPU が速くなるほど比率が上がり**、
> 語彙も増え続けている (Gemma 3 は 262,144)。

### 13 · `sampler-prefilter` — `host`

`common_sampler::set_logits` は毎トークン、語彙ぶんの `llama_token_data`
(12 B × 151,936 = 1.82 MB) を書き、順序を必要とする最初のサンプラーがそれを全部読み直す。
`llama_synchronize()` の後に走るので、**この間 GPU はアイドルであり、decode の 2.2% が
丸ごとクリティカルパスに乗っている**。

top-k がどうせ落とすものは、最初から作らない。生の logits を 1 回走査して、上位
`top_k + penalty_last_n` 個だけを拾う。penalties は logit を**下げるだけ**で、触る対象も
高々 `penalty_last_n` 個なので、この集合には必ず真の post-penalty top-k が含まれる。走査は
64 要素のブロックごとに**比較の OR** を取るだけなので、ほぼ全てのブロックがベクトル化された
1 パスで捨てられる。ここを max リダクションにすると 8 倍遅くなる。`std::max` は NaN を
またぐと結合的でないためコンパイラがベクトル化できず、直列の依存鎖になるからである
(1 トークンあたり 130 µs 対 19 µs)。

等価性が保証できないチェーン (grammar / logit_bias / mirostat / DRY / top-n-sigma /
top-k より前の未知のサンプラー) では、全語彙の構築に落とす。
停止スイッチ: `LLAMA_SAMPLER_PREFILTER=0`。

### 21 · `sched-reset-lazy` — `host`

`ggml_backend_sched_reset` はハッシュ表を丸ごと memset する。表は `graph_size` を基準に
6 万要素級で確保されるのに、1 グラフで埋まるのは数千要素なので、毎回 1 MB 以上を動かして
いた。同じビルドで比べると **`sched_reset` が 94 ms (1 回あたり 118 µs)、`alloc_graph` が
58 ms、`build_graph` が 8.5〜54.5 ms で、reset が最大の項**だった。

used ビットマップを走査して、使われた要素だけを戻す。未使用要素が `(-1, NULL)` であるという
不変条件は、`ggml_backend_sched_new` で 1 回作り、帰納的に保つ。

**+0.94%**、出力はビット一致する。

> P100 依存でも投機デコード依存でもない、**llama.cpp 一般の改善**である。

### 22 · `decode-sched-slots` — `host`

upstream はグラフ枠を 1 つしか持たないので、種別と `n_tokens` が毎ステップ変わる
ワークロードでは再利用が 14% しか当たらない (グラフ 1000 本あたり 140 ヒット)。
**sched が 1 本しか無い状態では、枠を増やしても意味がない。** 確保をやり直すことになり、
**1 ヒットあたり**の価値が 15 分の 1 になるからで、再利用率を 88% まで上げた実験でも
+0.21% しか出なかった。

枠ごとに sched を持たせると、本来の再利用に戻る (build / reset / split / alloc を丸ごと
飛ばせる)。

| 枠数 | 真の再利用 (グラフ 1000 本あたり) | dense A/B | VRAM |
|---:|---:|---|---:|
| 0 (upstream) | 140 | — | 基準 |
| **4** (既定) | 275 | **+0.97%** | +72 MiB |
| 8 | 295 | +1.35% | +132 MiB |
| 16 | 301 | — | — |

バックエンドサンプラーを持つ context では枠を一切使わない。サンプラーオブジェクトは
枠をまたいで共有される一方、最後に適用されたグラフの `ggml_tensor` ポインタを抱え込む
(`penalties` の `inp_token_ids` / `inp_counts`、`dist` の `inp_uniforms`)。`set_input` は
枠がヒットして再構築を飛ばした回も含め毎デコードそのポインタ経由で書き込むため、枠を
交互に使うと、ある枠のグラフが走っている最中に別の枠の入力を書くことになる。

トークン上限を 4 にしているのは、スロットのバッファがメインスケジューラとは別のレイアウトに
なる一方、`ggml_cuda_check_fusion_memory_ranges` が実際のテンソルアドレスから融合可否を
決めるためである。topk-moe の例外 (`ggml_nrows(node) <= TOPK_MOE_ROWS_PER_BLOCK`、
`v0.4.0` upstream では値 8) では、検証バッチの `n_draft + 1 = 5` はまだ例外の内側に収まる
——例外自体の境界は 5 ではなく `n_tokens = 9` にある——ので、実測の境界を説明するもの
ではない。実測では `n_tokens <= 4` で dense も MoE もビット一致を保ち、`n_tokens = 5` で
出力が変わった。`n_tokens <= 4` という上限はこの実測そのものであって、topk-moe の例外から
読み取った値ではない。

既定を 4 にしているのは、上振れと下振れが釣り合わないからである。VRAM の枯渇はモデルが
載らなくなる致命傷である一方、8 枠との差 0.38 ポイントは、実在するとはいえ
([benchmarking.ja.md](benchmarking.ja.md) で確立した ±0.07% の分解能は十分上回る)、
そのリスクに見合わない。VRAM に余裕があれば `LLAMA_DEC_SLOTS=8`、`=0` で upstream の挙動に
戻る。

`LLAMA_DEC_MAX_TOK` の既定値 4 はマジックナンバーではない。
`ggml_cuda_check_fusion_memory_ranges` は融合の可否を**実アドレス**で判定するので、バッファ
配置が変われば発火する融合が変わり、出力も変わる。topk-moe には
`nrows <= TOPK_MOE_ROWS_PER_BLOCK` (`v0.4.0` では = 8) ならアドレス判定を飛ばす例外があるが、
既定の 4 はこの例外の値から読み取ったものではない。実測で `n_tokens <= 4` ではビット一致し、
5 以上で変わる。

## モデル依存

### 15 · `mtp-draft-vocab` — `model`

**MTP のドラフトヘッドだけ**、語彙を部分集合に絞る。幅 1 の Q4_1 GEMV を grid X で分解すると、
その 12.7% は `output.weight` (606 MiB) というテンソル 1 本で、1 呼び出し 1188.8 µs =
535 GB/s、HBM2 ピークの 73% にあたる完全な帯域律速である。このうち 75% がドラフト側で、
decode の wall time の 8.1% を占める。

ドラフトに必要なのは自分の argmax と確率だけであり、**提案は必ずターゲットに検証される**。
したがって語彙を絞っても**ターゲットが何を受理するか**は変わらず、受理の頻度だけが下がる。
実証は、ドラフト幅を固定して浮動小数点演算の経路を揃えたうえで行った。既定の `p-min` では
ドラフトされるトークン**数**自体が変わるので、その条件でのバイト一致は主張していない。
`--spec-draft-p-min 0` (幅が固定され、浮動小数点演算の経路が揃う) では、3 プロンプトとも
縮小あり/なしで sha が完全に一致した。部分集合を 277 トークンまで削る極端なテストでは、
受理率が 0.01 まで落ちる一方、出力の sha は無傷だった。

**取り分は被覆率で決まり、被覆が崩れると負になる:**

| 被覆率 | 効果 |
|---:|---:|
| 97.5% | +8.3% |
| 92.8% | +5.9% |
| 90.3% | +3.9% |
| 54.2% | −3.3% |
| 33.5% | **−17.4%** |
| 29.7% | −14.6% |

部分集合は**文字種ごとに BPE ランクの上位を無条件で入れて**作ること。コーパスの頻度順だけで
作ると、そのコーパスに無い言語で崖から落ちる。しかも下振れには増幅機構がある。softmax の
分母が部分集合ぶんしか無いのでドラフトの確信度が過大に出て、p-min のゲートを通りやすくなり、
**外れるドラフトを余計に作る**からである。

`LLAMA_MTP_DRAFT_VOCAB` がトークンリストを指していなければ無効である。

パッチ 14 (`getrows-narrow-rows`) が前提である。`[n_vocab]` へ戻す展開が `ne00 = 1` の
`get_rows` になり、それが 278 µs かかって**全体で −29%** になっていた。
