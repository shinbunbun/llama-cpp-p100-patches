# パッチ一覧

English: [patches.md](patches.md)

llama.cpp `b10133` に対する 28 本のパッチ。以下は適用範囲で章立てしてあり、適用順は
ファイル名の番号である。**順序に意味がある** —
複数が同じファイルに触り、後のものが前のものの上に成り立っている。

各パッチは、それを正当化する実測値と**試して棄却した代案**を含めて、ソースに追加する
コメントにすべての根拠を持っている。このページはその索引である。

**適用範囲** は誰が得をするかの分類:

| 範囲 | 意味 |
|---|---|
| `sm_60` | Pascal GP100 に限定 (DP4A 無し、フルレートの HFMA2)。他では測らずに使わないこと |
| `pre-Volta` | Volta より前の NVIDIA、すなわち Pascal 以前に限定 |
| `pre-Turing` | Turing より前の NVIDIA に限定。**Volta を含む。Volta は tensor core を持ち、未実測である** |
| `all archs` | アーキテクチャで分岐していない。全 GPU に掛かる。実測は sm_60 のみ |
| `CUDA` | アーキテクチャ非依存の CUDA 改善 |
| `CUDA (delta-net)` | アーキテクチャ非依存だが、gated delta-net を持つモデルでしか発火しない |
| `host` | CPU 側。GPU が速いほど比率が上がる |
| `model` | ハードウェアではなくモデルアーキテクチャに依存 |

明記がない限り、出力は無パッチ版と**ビット一致**する。

## Pascal 固有

### 01 · `vmad-dp4a-sm60` — `sm_60`

sm_60 は DP4A を持たないので、upstream は 4×int8 内積をバイト取り出し + 乗算で
エミュレートしている。PTX `vmad` (byte-selector 付き scalar MAC) 4 連鎖なら
取り出しが要らず、約 15 → 約 6.75 SASS 命令になる。

**decode +6.5〜6.8%**。数値は完全一致。

### 02 · `mmvq-rows-per-block-sm60` — `pre-Turing`

MMVQ は出力 1 行あたり 1 ブロックなので、q8_1 の活性化行を出力行の数だけ L2 から
読み直している。pre-Turing NVIDIA では、DRAM 帯域 (ピークの 32〜34%) でも命令数でもなく
**このロード**が律速である。

ncols_dst 1 での掃引 (9B Q4_0、`llama-bench` tg32): 1 → 46.9、2 → 54.1、
**4 → 57.7 (+23.0%)**、8 → 57.2 t/s。

**shipped 値 4 でこの掃引の +23.0%**。2 行だった旧版は end-to-end で +15.4% (Q4_0) /
+16.5% (Q4_1) だった。+23.0% は `llama-bench tg32` の値であり、この harness には
投機デコードが無い ([benchmarking.ja.md](benchmarking.ja.md) 参照)。
Turing+ / GCN は上流の値のまま。

### 05 · `mmvf-f32-pascal` — `pre-Turing`

`mmvf.cu` は pre-Turing NVIDIA の F32 ベクトル経路を `ne11 <= 3` に制限しているが、
3 は**行列演算ユニットを持つ** GPU 用の値である。この関数の他の「行列演算ユニット無し」
分岐はすべて 8 を返し、呼び出し側のコメントも「tensor core が無い GPU では
ベクトルカーネルが有利」と書いている。Pascal は 1 つも持たない。

投機デコードは `ne11 = n_draft + 1 = 4` にするので上限を 1 つ超え、F32 の `mul_mat` が
すべて cuBLAS SGEMM に落ちていた (decode GPU 時間の 5.9%)。

**ワークロードにより +3.7〜4.3%**、3 回独立に再現。出力を確認した 1 ワークロードは
ビット一致 (かつ 3.6% 高速) だが、他は未確認である。編集対象の分岐は `cc < TURING` なので
Volta にも掛かるが、Volta は未実測である。

### 06 · `mmq-mul-mat-id-sm60` — `sm_60`

native DP4A が無いと MMQ は全面的に無効化される。**dense `MUL_MAT` についてはそれが正しい**:
n=512 で測った全量子化型 (測った範囲で) MMQ は cuBLAS 経路の 0.49〜0.61 倍しか出ず、全面有効化すると
dense モデルの prefill が 56% 失われる。

`MUL_MAT_ID` は事情が違う。そこでの代替は cuBLAS ですらなく sorted-gather 経路
(ストリーム同期 2 回 + ホストの三重ループ + expert ごとに `mul_mat` 1 回) なので、
0.6 倍のカーネルでも圧勝する。

**MoE prefill +20〜41%** (プロンプト 34〜23,908 トークンの全域で退行なし)、
ピーク VRAM 約 200 MiB 減。perplexity は統計的に区別できず (対応差分 ΔNLL +0.0028 ± 0.0029、t = 0.96)、CPU バックエンドを基準にすると**パッチ版の方が近い** (+0.038% 対 +0.224%)。

### 07 · `mmvq-moe-rows-sm60` — `all archs`

融合 MoE matvec の起動側にある `rows_per_block = 2; // 2 gives best perf based on tuning`
はハードコードでアーキ非依存であり、そのチューニングは DP4A 無しでは行われていない。
このカーネルは MoE の 1 decode ステップの 20.1% を占める。

**decode +1.9%**、prefill は無風 (MMQ を通るため)。

**これはアーキテクチャで分岐していない。** ただの `constexpr` なので全 GPU が 4 になり、
上流の 2 はどこにも残らない。実測は sm_60 のみである。Turing 以降で使うなら測るか戻すこと。

### 08 · `mmvq-mmid-batch-sm60` — `pre-Volta`

量子化 `MUL_MAT_ID` を融合 MoE matvec に回す条件の表は `cc < VOLTA` 一括なので、
sm_60 と sm_61 が同じ扱いになる。両者は「上限を超えた先の落ち先が妥当か」という
一点で決定的に違う。sm_61 は MMQ に落ちれば済むが、sm_60 は sorted-gather まで落ちる。

**+2.2%** (3 プロンプトの幾何平均、退行するワークロード無し)。

パッチ自身が書いている注意点を 2 つ、ここでも明示しておく。直接測ったのは IQ2_XS と
IQ3_XXS だけで、表全体を上げているのは理由 (sm_60 では落ち先がどの型でも遅い) が型に
依存しないからであって実測したからではない。これは論証であって測定ではなく、このパッチで
最も弱い部分である。もう 1 つ、表は `cc < VOLTA` 一括なので **sm_61 (P40 / GTX 10xx) でも
上限が外れる**。そこでは落ち先が MMQ なので、上の論証は当てはまらない。

### 09 · `mmvq-nwarps-small-k-sm60` — `pre-Turing`

ブロックは K に関係なく 4 ワープ幅だが、スレッドが K ループに入るのは
`tid/(qi/vdr) < ncols_x/qk` のときだけ。K が小さいとブロックの後半がカーネル全体を通じて
遊ぶ (K=512 の IQ3_XXS は 128 中 16 スレッドしか動いていなかった)。

ホスト側で「K を覆うのに必要な最小ワープ数」を渡すと: IQ3_XXS 64.03 → 36.64 µs、
Q3_K 106.59 → 48.27、IQ2_XS 24.00 → 20.76。

**MoE decode +1.29%。dense はノイズ内で不変 (+0.12%、下限 ±0.17%)**。`rows_per_block` を上げても直らない —
行は同じスレッドが内側ループで回すので、遊休スレッドは遊休のままである。

### 12 · `mmvq-f16-sm60` — `sm_60`

HFMA2 で作った Q4_1 GEMV。この中で最大のパッチ。GP100 では発行スロットあたりの MAC 数で
HFMA2 が VMAD の 4 倍になるので、ニブルを LOP3 のマジック定数だけで `half2` に展開し
(整数→浮動小数の変換命令をどこにも入れず)、fp16 で積む。

初版で**幅 5 で +9.4%**、改訂版 (形状によるワープ数選択と、20 バイトの `block_q4_1` が
撒いていた行あたり 64bit 乗算の除去) で **end-to-end +9.5%** — ノイズ内で同値だが、
より多くのワークロードで確認している。

この経路を通る幅では出力の最下位ビットが変わる (エピローグの変換を 2 回から 1 回に
したため)。ubatch 4 の perplexity は 7.2370 → 7.2359 (−0.015%) と動いた。これはスループット測定の
±2.9% の 200 分の 1 なので、確認ではなく**上限を与えている**にすぎない。無害である根拠は
上の脱量子化が厳密であること (Sterbenz) の側にある。

ノブ: `GGML_A16_NCOLS_MIN` / `GGML_A16_NCOLS_MAX` で幅の範囲を絞れば同一バイナリ内で
上流カーネルと比較できる。`GGML_A16_NWARPS` / `GGML_A16_QVEC` / `GGML_A16_SMALL_GRID` は
自動選択の上書き。

## アーキテクチャ非依存の CUDA

### 03 · `topk-moe-multirow` — `CUDA`

融合 MoE router カーネルは、出力が logits 入力とエイリアスするため 1 行に制限されている。
実際には `rows_per_block` (4) 行を 1 ブロックに載せ、各行を読み切ってから書いているので、
ブロック内バリアを 1 つ入れれば 1 ブロックが持つ全行まで安全に広げられる。

投機デコードは `n_draft + 1` 行を検証するのでここに正面から引っかかり、6 カーネルの
分解経路に落ちていた (decode GPU 時間の 4.0%、融合版なら 1.0%)。

**decode +2.8〜6.1%**。

**1 行を超える場合、出力はビット一致しない。** 融合カーネルが argsort 連鎖を置き換えるためで、
そもそも両者は expert 選択で食い違い得た。その食い違いが消えることが受理率の上昇の中身である。
上流が既に融合している `n_rows == 1` の経路は無改変でビット一致のままである。
このパッチについて perplexity は測っていない。

### 04 · `concat-non-cont-flat` — `CUDA`

非連続 concat のカーネルは 1 ブロックを `(i1, i2, i3)` に割り当て `i0` を `blockDim.x` で
回すので、`min(ne0, 256)` 本しか働かない。delta-net の conv 状態 concat は
`ne0 = 4..8` に対し `ne1 = 8192` なので、**32k 要素のコピーに 210 万スレッド**を起動し、
128 KiB が 33 µs (732 GB/s のカードで 4 GB/s) だった。

1 スレッド 1 出力要素に平坦化して **18.0 → 4.7 µs**、decode GPU 時間の 1.8%。

### 10 · `mmvq-q8-1-activation-cache` — `CUDA`

`ggml_cuda_mul_mat_vec_q` は呼び出しごとに `src1` を量子化し直すので、FFN の gate と up が
同じ活性化を 2 回量子化する。`quantize_row_q8_1_cuda` は `src0->type` を無視するので、
2 回目は 1 回目とバイト一致する。量子化の起動の 34.6% が重複だった。

**MoE decode +1.17% / dense +0.88%**。

代わりに上流の MMVQ 融合を Pascal で有効化する案は **−0.48% で棄却**した。融合は同じ重複を
消すが、2 つの重みを 1 カーネルに持つのでレジスタが増え (Q3_K 140 → 218)、占有率が 36%
落ちる。上流の「fusion is not universally faster on Pascal」は文字どおり正しい。
このパッチは効く半分だけを取っている。

### 14 · `getrows-narrow-rows` — `CUDA`

`get_rows` は gather 1 行につき 256 スレッドのブロックを 1 つ起動する。`ne00 = 1` では
248,320 ブロックが 1 要素ずつ運ぶ形になり 278 µs かかる。`(row, element)` を 1 次元に
潰せば 970 ブロックで済む。

### 16 · `cpy-fastdiv` — `CUDA`

`cpy_scalar` は 1 要素あたり 64bit 整数除算を 6 回する。マイクロベンチの形 (24,576 要素の
f32 コピー) で 4.94 µs ＝ 同じ形の自明なカーネルの 2.6 倍、40 GB/s ＝ 実測 read 帯域の 1/15。除数は
ループ不変なので、ggml が既に持つ `fastdiv` で置き換えられる。

**1 呼び出し 11.26 → 4.96 µs (−56%)**、end-to-end +0.82%。

### 17 · `norm-register-cache` — `CUDA`

`rms_norm_f32` / `l2_norm_f32` は `x` を 2 回読む (二乗和とスケール)。単トークン decode では
`grid = (1,1)` ＝ 56 SM のうち 1 個で、1 発 7.79 µs、decode の 1.9%。行をレジスタに持てば
2 回目の読みが消える。

**`rms_norm<1024>` 7.79 → 6.50 µs、`l2_norm<32>` 2.96 → 2.39 µs**、
+0.71% (dense) / +0.95% (MoE)。

`rms_norm` 側は `block_size >= 1024` のコンパイル時ゲートで切る。`l2_norm` 側は
ブロックサイズによらずキャッシュする。実行時ゲートでは負ける — 起動下限 1.9 µs の
カーネルでは、分岐の命令ぶんがそのまま約 6% の**コスト**として出る。

### 18 · `fuse-sibling-nodes` — `CUDA`

同形ノードの連続を 1 発にまとめる。topk-moe や rope+set_rows と違い**ノードを 1 つも
消さない**ので、必要なのは「並び順を入れ替えても結果が変わらないこと」だけで、
これをバイト範囲で実行時に確認する。

対象は連続する `CPY` (2.60 µs × 5 → 8.46 × 1) と `L2_NORM` (2.26 × 2 → 3.51 × 1)。
**+1.06%**、ビット一致。

停止: `GGML_CUDA_DISABLE_FUSE_CPY` / `GGML_CUDA_DISABLE_FUSE_L2_NORM`。
`GGML_CUDA_FUSE_LOG=1` で発火した規則を、`=2` で発火しなかった理由を出す。

### 19 · `fuse-pre-add-rms-norm` — `CUDA`

上流の融合は `rms_norm` の**後段**だけで、前段の残差加算は素通りしていた。
`add → rms_norm` は隣接ペアの最大で decode GPU 時間の 3.11%。`rms_norm` は 1 行 1 ブロック
なので、加算をそのプロローグでやれば済む。

`k_bin_bcast` 5,514 → 1,872 発。代わりに `rms_norm_f32<1024>` が 6.53 → 8.19 µs になる。
差し引き **+0.70%**、ビット一致。
停止: `GGML_CUDA_DISABLE_FUSE_PRE_ADD`。

### 20 · `fuse-add-unary-mul` — `CUDA`

`mul(unary(add(x, bias)), scale)` を 1 発にする。上流の UNARY+MUL 融合は
`ggml_are_same_shape` を要求するので `n_tokens > 1` で外れ、前段の ADD は常に素通りする。

`k_bin_bcast` 1,872 → **0 発**、カーネル総数 54,326 → 52,454。**+0.72%**、ビット一致。
停止: `GGML_CUDA_DISABLE_FUSE_ADD_UNARY_MUL`。

### 26 · `cpy-fused-rows` — `CUDA`

融合したコピーを 1 スレッド 1 要素から **1 スレッド 1 行**にする (dim0 が連続で上位次元が
密なとき)。添字計算が 1 要素あたり `fastdiv` 6 回から 1 行あたり乗算 1 回になる。

実形状での単体ベンチ (4 変種):

| | µs | GB/s |
|---|---:|---:|
| 1 スレッド 1 要素 (現行) | 8.92 | 110 |
| 1 スレッド 1 行、`ne0` は実行時 | 5.42 | 181 |
| 1 スレッド 1 行、`ne0` はコンパイル時定数 | **4.66** | **211** |
| 添字計算なし (上限) | 4.17 | 236 |

shipped コードは可能なら 3 行目を通る。これが **1.9 倍**である。
**律速はデータ量ではなく添字計算**であり、上限まではあと 12% しかない。
停止: `GGML_CUDA_DISABLE_CPY_ROWS`。

### 28 · `top-k-partial` — `CUDA`

`ggml_top_k` は `cub::DeviceTopK::MaxPairs` を使うが、これは **CCCL >= 3.2 を要求する**。
CCCL 3.x は CUDA 13 に同梱されるので、**CUDA 12.x のどのリリースでも**立たず、
`argsort_f32_i32_cuda_cub` にフォールバックして
**語彙を完全に基数ソートして先頭 k 個を取る**。投機デコードではこれが k=10・語彙 151,936 で
毎トークン走り、約 172 µs ＝ decode の 1.1% になる。

代わりに 2 段の部分選択にする。比較は cub と同じ単調 uint32 写像で行い、key を上位 32bit・
`~idx` を下位 32bit に詰めるので、**単純な符号なし比較だけ**で cub の stable な順序を
±0 や NaN まで再現する。結果はビット一致。

単体ベンチ (n=151,936): cub の全ソート 157.2 µs 対 **k=10 で 20.6 µs (7.6 倍)**、
全ソートとの不一致 0。

速くするのに効いたのは 2 つで、どちらも実測で判明した。①ブロック全体のツリーリダクションを
warp shuffle に置き換える (70.9 → 42.1 µs ＝ k ラウンドぶんの barrier が律速だった)、
②64bit に詰めて分岐なしの shuffle 1 本にする (42.1 → 20.6)。1 スレッドの受け持ち要素数は
ほぼ無関係 — 作業量ではなくラウンドごとのレイテンシ律速である。

k > 16 (候補をスレッドのレジスタ配列に置く実装上の上限)、行が短い場合、グリッドが
大きすぎる場合は従来のソート経路に落とす。
停止: `GGML_CUDA_DISABLE_TOP_K_PARTIAL`。

> これは Pascal 以外にも効く。**CUDA 12.x で GPU サンプリングを使う全員が、
> 毎トークン語彙全体のソートを払っている。**

## delta-net / gated delta-net (Qwen3-Next / Qwen3.5)

以下はアーキテクチャ非依存の CUDA 変更だが、gated delta-net の linear-attention を持つ
モデルでしか発火しない。

### 23 · `fuse-gdn-beta-sigmoid` — `CUDA`

`beta = sigmoid(x)` を `gated_delta_net` に畳む。`unary_op_kernel<op_sigmoid>` は
`gated_delta_net_cuda` と**同数** (4,080 発、6.86 ms) 起動され、うち 4,032 が `grid = 1`
＝ 全体が起動の固定費だった。gdn は既に `g` 側の `expf` を畳んでいる。

node-preserving (gdn が畳んだノードの dst も書く) なので使用回数の解析は不要で、
結果はビット一致する。
停止: `GGML_CUDA_DISABLE_FUSE_GDN_BETA`。

### 24 · `fuse-gdn-state-gather` — `CUDA`

SSM state の `GET_ROWS` (2 MB の gather) を `gated_delta_net` に畳む。
`k_get_rows_float_vec` は gdn と同数 (3,984 発、46.24 ms、decode の 1.4%) 起動され、
中身は「キャッシュから 2 MB コピーして渡すだけ」の往復だった。gdn は既に**新しい** state を
キャッシュへ直接書いているので、入力側も直接読む。

`GET_ROWS` は 10 ノード手前にあるので、**ノードの実行を後回しにして消費側に畳む機構**を
入れている。並行ストリーム使用時は順序入れ替えが危険なので無効化する。
停止: `GGML_CUDA_DISABLE_FUSE_GDN_GATHER`。

### 25 · `gdn-gather-single-snapshot` — `CUDA`

行番号の退避を層ごとではなくグラフ 1 本につき 1 回にする。全 SSM 層が同じインデックス
テンソルを使うので、層ごとにやると DtoD コピーが 4,080 発 (+7.31 ms) 増える。

### 27 · `fuse-concat-gather` — `CUDA`

conv 状態の `GET_ROWS` を直後の `CONCAT` に畳む (そのために `dim == 0` の CONCAT を
1 スレッド 1 行にする)。`build_conv_state` は 96 KB の行を gather して即 concat する往復で、
両カーネルとも 42 / 51 GB/s ＝ 天井の 7〜8% しか出ておらず、律速は添字の割り戻しだった
(`concat_cont<T,0>` は `ne0` がたった 4 なのに **64bit の実行時除算**をしていて、
GP100 には 64bit 除算器が無い)。

単体ベンチ: 2 カーネルで 7.203 µs → **融合 2.819 (−61%)**。

**行単位化だけではヌルである** (平均 +0.006%、8 ラウンド中 正 3 本)。1 スレッド 1 行が
単体で得なのは dst 行がちょうど 16 B ＝ ベクトルストア 1 発になるときだけ。
行単位**＋融合**は平均 +0.74%、8 ラウンド中 正 7 本 — カーネル 1 発が丸ごと消えるからである。
したがって融合しない経路は 16 B の行だけに絞ってある。

停止: `GGML_CUDA_DISABLE_CONCAT_ROWS` / `GGML_CUDA_DISABLE_FUSE_CONCAT_GATHER`。

## ホスト側

### 11 · `penalties-direct` — `host`

`llama_sampler_penalties_apply` は候補 1 つずつ `unordered_map` を引くが、map の要素数は
高々 `penalty_last_n` (既定 64) で、候補リストは語彙全体である。語彙 151,936 では
**候補ごとに 1 回 hash lookup して当たるのは最大 64 件** ＝ おおよそ 2,400 回に 1 回しか
仕事をしない。**1 トークンあたり 0.78 ms、スループットの 5.3%**。

代わりにペナルティ対象のトークン側を走る。各要素について `cur_p->data[id].id == id` を
確認 (高々 64 回の比較) し、1 つでも外れたら元の全走査に落ちる。適用される演算とその順序は
同じなので出力はビット一致する。

> これも Pascal 以外に効く。ホスト側なので **GPU が速くなるほど比率が上がり**、
> 語彙も増え続けている (Gemma 3 は 262,144)。

### 13 · `sampler-prefilter` — `host`

`common_sampler::set_logits` は毎トークン語彙ぶんの `llama_token_data`
(12 B × 151,936 = 1.82 MB) を書き、最初に順序を要るサンプラがそれを全部読み直す。
`llama_synchronize()` の後に走るので **GPU はこの間アイドル ＝ decode の 2.2% が丸ごと
クリティカルパス**である。

top-k が落とすものは最初から作らない。生の logits を 1 回走査して上位
`top_k + penalty_last_n` だけ拾う。penalties は logit を**下げるだけ**で触る対象は高々
`penalty_last_n` 個なので、その集合には必ず真の post-penalty top-k が含まれる。走査は 64 要素ブロックごとに
**比較の OR** を取るだけなので、ほぼ全ブロックがベクトル化された 1 パスで捨てられる。
ここで max リダクションにすると 8 倍遅い — `std::max` は NaN をまたいで結合的でないので
コンパイラがベクトル化せず、直列の依存鎖になる (1 トークンあたり 130 µs 対 19 µs)。

等価でないチェーン (grammar / logit_bias / mirostat / DRY / top-n-sigma / top-k 前の
未知のサンプラ) では全語彙構築に落ちる。
停止: `LLAMA_SAMPLER_PREFILTER=0`。

### 21 · `sched-reset-lazy` — `host`

`ggml_backend_sched_reset` はハッシュ表を丸ごと memset する。表は `graph_size` 基準で
6 万要素級に確保されるのに 1 グラフで埋まるのは数千要素なので、毎回 1 MB 以上動かしていた。
同じビルドで比べると **`sched_reset` 94 ms (118 µs/回) 対 `alloc_graph` 58 ms 対
`build_graph` 8.5〜54.5 ms ＝ reset が最大項**だった。

used ビットマップを走って使われた要素だけ戻す。未使用要素が `(-1, NULL)` である不変条件は
`ggml_backend_sched_new` で 1 回作り、帰納的に保つ。

**+0.94%**、ビット一致。

> P100 依存でも投機デコード依存でもない、**llama.cpp 一般の改善**である。

### 22 · `decode-sched-slots` — `host`

上流はグラフ枠を 1 つしか持たないので、種別と `n_tokens` が毎ステップ変わるワークロードでは
再利用が 14% しか当たらない (グラフ 1000 本あたり 140 ヒット)。**sched が 1 本しか無いと
枠を増やしても意味がない** — 確保をやり直すことになり、**1 ヒットあたり**の価値が 15 分の 1 に
なる。再利用率 88% まで上げた実験でも +0.21% しか出なかった。

枠ごとに sched を持たせると本来の再利用に戻る (build / reset / split / alloc を丸ごと飛ばす)。

| 枠数 | 真の再利用 (グラフ 1000 本あたり) | dense A/B | VRAM |
|---:|---:|---|---:|
| 0 (上流) | 140 | — | 基準 |
| **4** (既定) | 275 | **+0.97%** | +72 MiB |
| 8 | 295 | +1.35% | +132 MiB |
| 16 | 301 | — | — |

既定が 4 なのは非対称性が厳しいためである。VRAM 枯渇はモデルが載らない致命傷である一方、
0.38 ポイントは — 実在し、[benchmarking.ja.md](benchmarking.ja.md) で確立した ±0.07% の
分解能を十分上回るが — そのリスクに見合わない。余裕があれば `LLAMA_DEC_SLOTS=8`、`=0` で上流の挙動に戻る。

`LLAMA_DEC_MAX_TOK` の既定 4 はマジックナンバーではない。
`ggml_cuda_check_fusion_memory_ranges` は融合の可否を**実アドレス**で判定するので、
バッファ配置が変われば発火する融合が変わり、出力も変わる。topk-moe には
`nrows <= GGML_CUDA_TOPK_MOE_ROWS_PER_BLOCK` (= 4) ならアドレス判定を飛ばす例外があり、
その中に収まる限り配置は関係ない — 実測でも `n_tokens <= 4` ではビット一致、5 以上で変わる。

## モデル依存

### 15 · `mtp-draft-vocab` — `model`

**MTP ドラフトヘッドだけ**語彙を部分集合に絞る。幅 1 の Q4_1 GEMV を grid X で分解すると、
その 12.7% は `output.weight` (606 MiB) 1 テンソルで、1 呼び出し 1188.8 µs = 535 GB/s ＝
HBM2 ピークの 73% ＝ 完全な帯域律速である。うち 75% がドラフト側で、decode wall の 8.1%。

ドラフトが要るのは自分の argmax と確率だけで、**提案は必ずターゲットに検証される**。
だから語彙を絞っても**ターゲットが何を受理するか**は変わらず、受理の頻度だけが下がる。
下の実証はドラフト幅を固定して FP の経路を揃えたものである。既定の `p-min` では
ドラフトされるトークン**数**が変わるので、そこでのバイト一致は主張していない。実証: `--spec-draft-p-min 0`
(幅固定 = FP の経路が揃う) では 3 プロンプトとも縮小あり/なしで sha 完全一致。部分集合を
277 トークンまで削る退化テストでは受理率が 0.01 まで落ちる一方、出力 sha は無傷だった。

**取り分は被覆率で決まり、被覆が崩れると負になる:**

| 被覆率 | 効果 |
|---:|---:|
| 97.5% | +8.3% |
| 92.8% | +5.9% |
| 90.3% | +3.9% |
| 54.2% | −3.3% |
| 33.5% | **−17.4%** |
| 29.7% | −14.6% |

部分集合は**文字種ごとに BPE ランク上位を無条件で入れて**作ること。コーパス頻度順だけだと、
コーパスに無い言語で崖を踏む。下振れには増幅装置がある — softmax の分母が部分集合ぶんしか
無いのでドラフトの確信度が過大に出て、p-min ゲートが通りやすくなり、**外れるドラフトを
余計に作る**。

`LLAMA_MTP_DRAFT_VOCAB` がトークンリストを指していなければ無効。

パッチ 14 (`getrows-narrow-rows`) が前提である。`[n_vocab]` へ戻す展開が `ne00 = 1` の
`get_rows` になり、それが 278 µs かかって**全体で −29%** になっていた。
